P1

Sewadaar Directory

Volunteer & devotional‑service management platform for a Monastery/Ashram

FlutterDartKotlinSpring WebFluxR2DBCPostgreSQLAWS S3DockerJWT

The problem

Volunteers (sewadaars) serve in many daily devotional‑service duties (sewas) — gates, halls, kitchens, medical desks, security. Coordination ran on spreadsheets and messages, so nobody had one trustworthy view of who serves where and when.

The solution

A single secure system of record: a reactive Kotlin / Spring WebFlux API with PostgreSQL and a Flutter client for web and mobile. It manages 880+ volunteers, their photos and documents, and their assignments to duties with explicit coordinator and volunteer roles.

My role

Sole engineer — data model, backend, API security, Flutter UI, S3 storage, Docker environment and release.

What I built

  • Duty & volunteer management with per‑assignment time windows validated against the duty’s hours
  • Schedule (roster) view — a colour‑coded daily timeline across morning, afternoon, evening and night
  • Approval workflow for new volunteers: pending approval → document verification → active, with enforced transitions
  • Secure photo & document storage on AWS S3 using time‑limited presigned URLs
  • Bilingual PDF generation — English / Hindi declaration & affidavit documents
  • Search, filters & pagination over names, phones, skills and status
  • Responsive Flutter UI — split‑pane on desktop, full‑screen flows on mobile
Security
Server‑enforced role‑based visibility

Coordinators see only the duties and volunteers they manage; admins see everything. Rules live in the API and SQL queries — not just the UI — so changing IDs or parameters can’t bypass them.

Auth
JWT with refresh tokens & single sessions

Short‑lived access tokens, rotating refresh flow and single‑device session enforcement, with roles resolved on every request.

Backend
Reactive & parameter‑safe

Spring WebFlux + R2DBC end‑to‑end; dynamic search built with bound parameters and Postgres array operators.

DevOps
Reproducible local stack

Docker Compose with PostgreSQL and LocalStack S3, so the full photo/document path runs without cloud credentials.

P2

Monastery/Ashram Expense Manager

Expense request, multi‑level approval & disbursement platform

React 19TypeScriptViteMUIKotlinSpring WebFluxPostgreSQLFlywayAWS S3Docker

The problem

Saints’ everyday expenses — groceries, medicines, travel, repairs, festival material — were requested informally and paid from a shared fund, with little traceability about who approved what, how much was actually paid and when.

The solution

A full‑stack platform that digitises the whole request‑to‑payout cycle. Volunteers raise itemised cases on behalf of saints, admins review line‑by‑line, and a super admin gives final approval and records payments — fully or in instalments — leaving a clear audit trail at every step.

My role

Sole engineer — database schema and migrations, reactive backend, role‑based workflow, React UI, charts and reports, scheduler and Docker deployment.

What I built

  • Three‑stage workflow — Volunteer creates → Admin claims & reviews → Super Admin approves & pays
  • Item‑level decisions — approve, partially approve or reject each line with its own amount
  • Disbursement tracking — cash, bank transfer or UPI with references; status moves to partially/fully disbursed automatically
  • Automated recurring cases — an hourly scheduler spawns monthly templates with correct IST/UTC handling
  • Reports & analytics — spend trend, category doughnut, saint‑wise cases, volume ranking, category buckets, aggregated payments
  • Notifications, user management, category taxonomy and saint profiles with documents
  • Installable PWA with a responsive layout for phones

Workflow
State machine with guarded transitions

Statuses (Created → Submitted → Admin‑approved → Super‑admin‑approved → Partially / Fully disbursed, or Rejected) are enforced server‑side per role.

Data
Versioned schema with Flyway

Nine incremental migrations — enums, soft deletes, deadlines, item‑level attachments — keep every environment in lock‑step.

Automation
Timezone‑correct scheduler

Recurring templates fire at an IST hour, store UTC, and advance month‑by‑month — a subtle bug fixed after tracing a 5½‑hour drift.

Storage
S3 or local, behind one interface

A storage abstraction swaps S3 for the filesystem in dev, so uploads work everywhere with zero code changes.
